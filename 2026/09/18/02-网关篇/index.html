1. GateServer

GateServer网关服务入口，主函数
读取配置 → 创建 asio 事件循环 → 启动 Tcp 服务，并且捕获Ctrl+C/kill 信号优雅退出。

初始化方式

  1. {}：列表初始化，C++11 新增，会做窄转换检查，不允许隐式窄化
  2. ()：直接初始化，传统 C++ 写法，允许数值窄转换
  3. 1这个参数叫 concurrency_hint（并发提示），类型 std::size_t。

    它不是强制创建 N 个线程，只是给 asio 的一个建议值：提示 asio，你打算用多少个线程来调用 ioc.run()。

##net::signal_set signals(ioc, SIGINT, SIGTERM);

创建一个信号集合，绑定到 io_context ioc，监听 SIGINT 和 SIGTERM 两个信号。

  1. SIGINT：SIGnal INTerrupt
    控制台按下 Ctrl + C，终端发给程序的中断信号。
  2. SIGTERM：SIGnal TERMinate
    执行 kill 进程pid（不带 - 9），操作系统优雅终止信号。kill -9 是SIGKILL，无法被捕获，程序直接被内核干掉，没有机会执行收尾代码。

signal_set::async_wait()：异步等待信号事件

  • 调用之后不会阻塞当前线程，函数立刻返回；
  • 只是向 asio 事件循环注册一个回调函数；
  • 当操作系统发来我们监听的信号（SIGINT/SIGTERM），Asio 内部捕获，填充参数,这个 lambda 回调会被投递到ioc的任务队列，在ioc.run()的线程里执行。
  • if(error) == true：异步任务异常，直接 return，不执行 ioc.stop ()
  • if(error) == false：正常捕获到系统信号，继续执行 ioc.stop() 来优雅退出
  • ioc.stop();,把 io_context 标记为停止状态
    1. 不会立刻终止正在执行的回调；
    2. 不再接收新的异步任务；
    3. 当前队列中已经就绪的回调全部执行完，ioc.run()就会返回，解除阻塞。

这是一个 INI 配置文件管理器，用 Boost.PropertyTree 实现，采用饿汉单例，作用：读取 config.ini，把 [section] key=value 加载到内存 map，支持类似数组的 mgr["分区"]["键"] 读写配置。

  1. SectionInfo：代表 INI 里一个 [section 分区]，内部保存这个分区下所有 key-value 字符串。
  2. ConfigMgr：全局配置管理器（单例），保存所有 section。

说明:

  • 懒汉单例，局部静态变量
  • 饿汉：程序启动前就创建实例
  • 懒汉：第一次调用 GetInstance 才创建实例，call_once/Meyers/DCL 全部属于懒汉。

std::map

  • 头文件：#include <map>
  • std::map<KeyType, ValueType> 是有序关联容器，底层是红黑树
    -特点：
    1. key 唯一，不能重复；
    2. 元素按照 key 自动升序排序（默认std::less<Key>）；
    3. 查找、插入、删除：O(logN)；
    4. 键值对：pair<const Key, T>，key 不能修改，value 可以修改。

-api
1.find (key)
- 参数：key
- 返回：迭代器 iterator
- 找到：迭代器指向 pair<const Key, T>
- 找不到：返回 m.end ()
- 只查询，不会插入任何元素！[]会覆盖 value
2.insert () 插入元素
- 返回值：pair<iterator, bool>
- bool：true = 插入成功（原来没有这个 key）
- bool：false = 插入失败（key 已存在，不覆盖旧值）
3.clear()
清空 map 中所有元素，size 变为 0；容器本身不销毁。

CServer

CServer 是网关服务的监听管理器，负责端口监听、接受 TCP 客户端连接，不处理具体 HTTP 报文读写；连接建立后把读写任务交给 HttpConnection，并且使用 io_context 线程池分担连接业务压力。

1. 奇异递归模板 CRTP

  • std::enable_shared_from_this<CServer> —— 奇异递归模板 CRTP

    作用：让 CServer 对象可以在自身成员函数内部，安全拿到指向自己的shared_ptr，函数调用 shared_from_this()。

2. boost::asio::ip::tcp::acceptor

  • acceptor（接收器 / 监听器），作用：开启端口监听，等待 TCP 客户端发起连接请求，完成三次握手，拿到新的 tcp socket。
  • _acceptor(ioc, tcp::endpoint(tcp::v4(), port):只传协议 + 端口，没有指定 IP 地址 → 默认监听 0.0.0.0

3. boost::asio::ip::tcp::endpoint

封装 IP 地址 + 端口号，代表 TCP 通信一端的地址信息。服务端用来 bind 监听地址；客户端用来指定要连接的服务端地址。

4. auto& io_context = AsioIOServicePool::GetInstance()->GetIOService();

从io_context 池（AsioIOServicePool，单例）里取出一个io_context的引用，分配给即将新建的 Http 连接。

5. tcp::acceptor::async_accept(Socket& peer_socket, Handler&& handler)

说明

  • 本次回调执行完之后，这个 lambda 不会再触发；但是代码在回调里面调用了 self->Start()，会注册一轮全新的 async_accept，等待下一个新客户端连接，下一次连接事件到来会触发新的回调。
  • 每次 async_accept 只对应一次回调。一次回调执行完毕，这个异步任务就结束了，不会自动重复触发。想要持续监听，必须手动再次注册 async_accept。

6. io_context（IO 上下文） 和 socket 的关系

每个 tcp::socket 在创建的时候，必须绑定一个 io_context（执行器 executor）；socket 所有的异步事件（async_read /async_write），都会交给它绑定的这个 io_context 去调度执行。

7. acceptor、io_context、socket 三者关系

io_context 是事件调度器；acceptor 是 TCP 监听器，socket 是 TCP 通信端点；acceptor 和 socket 各自绑定 io_context，acceptor 负责接收连接，把新连接填入 socket，socket 负责收发数据。acceptor 绑定的 io 和 socket 绑定的 io 可以不是同一个（你的项目就是这种）。

io_context（IO 上下文）

作用：事件队列 + 回调调度器

  • 里面存放异步任务；调用io_context.run()的线程会取出任务、执行回调。
  • 所有 asio 对象（acceptor、socket）创建时必须绑定一个 io_context，不能悬空。
  • 一个 io_context 可以被多个 acceptor/socket 共用。

acceptor（tcp::acceptor，监听器）

  • 本质是listen 监听 socket，只负责监听端口、接收 TCP 连接，不收发业务数据。
  • 创建时绑定一个 io_context（你代码中是主线程的 ioc）。
  • acceptor 的async_accept事件、accept 回调，由它自己绑定的 io_context 调度（主线程执行 accept 回调）。
  • acceptor 的职责：当客户端三次握手完成，把新连接填充进你预先传入的 socket 对象。

⚠️ acceptor不会修改 socket 原本绑定的 io_context。

socket（tcp::socket，数据套接字）

  • 用来和单个客户端做数据读写（http 的收发）。
  • 创建的时候就绑定好 io_context（你代码里是 IO 池取出的 io_context，对应子线程），绑定后不可更换。
  • socket 的async_read / async_write等读写回调，由 socket 自己绑定的 io_context 调度（IO 池子线程）。

AsioIOServicePool

AsioIOServicePool 是基于 boost asio 实现的 io_context 线程池（IO 池），单例模式。预先创建一批io_context+ 工作线程；对外通过轮询，分配 io_context 给新连接，让不同 TCP 连接的读写事件分散在多个线程执行，充分利用多核 CPU，解决单 io_context 单线程串行处理的性能瓶颈。

CServer的acceptor 跑主线程 io，每一条新连接拿到池子里的一个 io_context，socket 绑定这个 io，读写回调在池子子线程跑。

_ioServices[i].run();

_ioServices[i] 是一个 boost::asio::io_context 对象。run() 是 io_context 的事件循环入口函数。

  1. run() 会阻塞当前调用它的线程；
  2. 不断从这个 io_context 的任务队列取出异步回调任务，在当前线程执行；
  3. 当满足退出条件时，run() 解除阻塞，函数返回，线程继续往下执行。

io_context 会不会被 “占用完”？

  • io_context 本身不是一次性资源，不会被取走消耗掉。

  • 池子里的 io_context 是常驻对象，GetIOService 只是返回它的引用，不是转移所有权，不是拿走、不是消费掉。

  • 多个 HttpConnection、多个 socket可以同时拿到同一个 io_context 引用，共用同一个 io。

  • 代码里一个 io_context 绑定一个独立工作线程

  • 同一个 io 上的所有异步回调，在对应的工作线程串行执行；

  • 多个连接共用同一个 io 是正常现象，只是负载均衡分摊。

  • 池子的 io 数量固定，不会动态新增；新连接来了只是复用现有的 io，不存在资源耗尽。

executor_work_guard 保活守卫

_works 保存一批 executor_work_guard 保活守卫，用来阻止 io_context.run() 在任务队列为空时自动返回，让 IO 工作线程常驻，持续等待新的异步网络事件。

HttpConnection

单条 HTTP TCP 连接的封装类，基于 Boost.Beast，负责一条客户端 TCP 连接上 HTTP 报文的读写、参数解析、超时管控，把原始网络事件转化为业务请求，交给 LogicSystem 处理，采用短连接模型。

说明

beast::flat_buffer _buffer{ 8192 };

  • flat_buffer 是 Boost.Beast 提供的连续内存缓冲区，专门给 Beast 的 http/websocket 读写函数使用；{8192} 设置初始容量 8192 字节，用来存放从 socket 读到的 HTTP 原始字节流。

  • {8192} 含义：初始预分配内存大小 8192（8KB）

    1. 只是初始容量，不是上限！
    2. 如果收到的 http 报文大于 8KB，flat_buffer 会自动扩容，重新分配更大的连续内存，拷贝旧数据。
    3. 预分配 8K 目的：大部分普通 HTTP 请求很小，提前开好内存，减少频繁扩容带来的内存拷贝开销。

http::request<http::dynamic_body> _request;

  • http::request 是 Boost.Beast 封装的 HTTP 请求报文对象；模板参数 dynamic_body 指定请求体 (body) 的存储策略，body 内存可以动态增长，大小不固定。
  • 里面包含请求行（method、url、http 版本）、请求头 headers、请求体 body三大部分；

http::response<http::dynamic_body> _response;

Boost.Beast 的 HTTP 响应报文对象模板，dynamic_body 表示响应体内存动态扩容，用来组装要返回给浏览器 / 客户端的完整 HTTP 响应报文，最后交给http::async_write发送。

net::steady_timer deadline_{_socket.get_executor(), std::chrono::seconds(60) };

Asio 的 steady_timer（稳定时钟定时器），绑定和 socket 相同的执行器，初始 60 秒超时，用来做 HTTP 连接的超时保护，防止僵死 / 半开连接。

http::async_read(_socket, _buffer, _request, callback);

  1. 操作系统内核把客户端发的 TCP 数据拷贝到应用层，先写入 _buffer
  2. Beast 从 _buffer 里面拿原始字节，解析 HTTP 协议，把解析出来的结构化信息填充到 _request 对象
  3. 解析完成后：
    • _buffer 里还残留原始字节（可能有粘包，或者本次读完剩下的数据）
    • _request 是结构化对象（method、url、header、body），和 buffer 是分开的

http::async_write

说明

把**已经组装好的 _response（http 响应对象）**异步发送给客户端。

1. auto self = shared_from_this();

捕获当前HttpConnection的智能指针，保证异步回调执行的时候，HttpConnection 对象不会被析构。

因为 HttpConnection 继承enable_shared_from_this，必须用 shared_from_this。

2. _response.content_length(_response.body().size());

手动设置 HTTP 响应头 Content-Length，值等于响应 body 的字节大小。
HTTP/1.1 短连接场景下，客户端靠这个长度判断响应什么时候接收完毕。

如果不设置 Content-Length，客户端不知道数据包什么时候结束，会卡住等待

3. http::async_write(_socket, _response, 回调)

异步写接口：

  • 把_response对象序列化成 HTTP 原始字节
  • 通过tcp::socket发给客户端
  • 发送完成（成功 / 失败）才会执行回调，async_write 是非阻塞，函数立刻返回，不会等发送完

LogicSystem

路由 + 业务逻辑单例类

  • 和HttpConnection职责分离：HttpConnection 只管网络 IO、协议解析；LogicSystem 负责URL 路由、业务处理
  • 全局唯一（继承Singleton单例），程序启动时构造函数执行，一次性注册全部路由回调

一句话：接收 HttpConnection 传过来的请求路径，匹配对应的业务回调函数，执行业务，填充connection->_response。

路由（Web 路由）

路由 = 根据 HTTP 请求的【请求方法 + URL 路径】，找到对应的业务代码去执行。

Redis 和 MySQL

MySQL 是持久化主数据库（存真实、永久数据）；Redis 是高速缓存 / 临时存储，用来扛压力、减少 MySQL 访问，放短期临时数据。二者是「缓存 + 数据库」的搭配，也就是经典的缓存架构。

gRPC

gRPC 是谷歌开源的、基于 HTTP2 的远程过程调用框架。简单理解：可以像调用本地函数一样，去调用另一台服务器上的函数。

Http 服务 和 验证码服务 是两个独立程序，可能跑在同一台机器，也可能不同机器。
Http 服务想要调用验证码服务的能力，就用 gRPC。

1.获取验证码接口

GetVarifyRsp rsp = VerifyGrpcClient::GetInstance()->GetVarifyCode(email);

看上去像是调用本地函数GetVarifyCode(email)，实际上这个函数内部，会通过网络，把 email 发给验证码微服务，远端执行，然后把结果传回。

2.用户登录接口

auto reply = StatusGrpcClient::GetInstance()->GetChatServer(userInfo.uid);

调用 Status 微服务，根据用户 uid 分配聊天服务器，返回 token、服务 ip 端口。

message.proto

这是 protobuf3（proto3） 的定义文件 message.proto。

作用：定义微服务之间 gRPC 调用的接口、请求结构体、响应结构体。

gRPC 工具可以根据这个文件自动生成 C++（也支持 Java/Python 等）的服务端、客户端代码，你前面看到的 VarifyService::Stub、GetVarifyReq、GetVarifyRsp 全部都是工具自动生成出来的。

proto 就是一份接口契约：客户端和服务端统一遵守这份定义，两边序列化 / 反序列化二进制数据。

IM 全称：Instant Message，即时通讯

IM 就是实时聊天系统，支持双向收发消息，像微信、QQ 就是 IM 应用。

  1. std::unique_lock<std::mutex> lock(mutex_)
  • std::condition_variable 强制要求搭配 unique_lock，不能用lock_guard，因为wait内部需要临时解锁、之后重新上锁；lock_guard 不支持动态解锁。
  • 执行到这一行：mutex 立刻上锁，其他线程进入 getConnection/returnConnection 都会阻塞在这。
  1. cond_.wait (lock, 谓词 lambda)

wait 做的事情：

  1. 先判断 lambda 返回值；
  2. 如果返回false → 释放 mutex 锁，当前线程休眠阻塞；
  3. 被其他线程cond_.notify_one()唤醒后，重新抢到锁，再次执行 lambda 判断；
  4. 只有 lambda 返回true，wait 才解除阻塞，继续往下执行代码。

说明

队列中存放：unique_ptr<VarifyService::Stub>，所有权还在 queue 内部，没有转移出去。

  1. pop()：取出队首的 unique_ptr<Stub>，把它从 queue 容器移除；
  2. 这个临时的unique_ptr对象在 pop 执行完的瞬间就销毁；
  3. unique_ptr 析构 → 释放底层的Stub对象 → Stub 内部shared_ptr<Channel>引用计数减 1。

pop() 本身不会专门去写代码销毁 Stub，销毁的是队列里存储的那个 unique_ptr<Stub> 对象。
而 unique_ptr 是 RAII 智能指针，unique_ptr 自身被销毁的时候，自动 delete 它管理的 Stub。

说明

  1. std::move：把队列里 unique_ptr 的所有权转移出去，队列里面的 unique_ptr 变成空 (nullptr)；
  2. pop()：把这个已经掏空、空的 unique_ptr 从队列删掉；
  3. 被管理的 Stub不会销毁，所有权现在在局部变量context手里，函数 return 之后交给上层使用。

RedisMgr

缓存验证码，设置过期时间

说明

预先创建指定数量的 Redis 连接，逐个建立 TCP 连接、做 Redis 密码 AUTH 认证；连接创建 + 认证成功的连接放入队列，失败的直接释放丢弃；最终得到一个存放可用 redisContext * 的连接池队列。

redisCommand 产生的 redisReply 是堆内存，必须手动释放！
不管成功失败，只要 reply 不是 nullptr，都要调用freeReplyObject，否则内存泄漏。

MysqlDao

MYSQL

MYSQL 是 libmysqlclient（MySQL C 客户端库） 定义的结构体，MYSQL* 就是它的指针，叫做 MySQL 句柄，代表一条 MySQL 客户端连接实例。

MYSQL_STMT*

MYSQL_STMT* 是 MySQL C 客户端库（libmysql）提供的预处理语句句柄指针，全称 Prepared Statement（预处理语句），专门用来执行带占位符?的 SQL，核心目的：防 SQL 注入，也可复用 SQL 模板提升性能。

预处理语句：SQL 模板和参数分开传输。

SQL 注入

SQL 注入就是攻击者通过输入恶意内容，把原本的 “数据” 变成可执行的 SQL 代码，篡改后端原本要执行的 SQL 语句，非法查询 / 删除 / 修改数据库数据。
