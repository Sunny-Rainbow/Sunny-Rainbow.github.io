CUDA CONCURRENCY（并发）

Pinned Memory（页锁定内存/不可分页内存）

Pinned Memory带来的能力：

  • host和device这几件的数据拷贝速度更快
  • 内存拷贝可以和 CPU 异步执行（CPU 不用等待拷贝完成）
  • 内存拷贝可以和 GPU 异步执行

使用方法：

  • cudaHostAlloc / cudaFreeHost（直接分配页锁定内存 / 释放页锁定内存），代替malloc / free or new / delete

  • cudaHostRegister / cudaHostUnregister（将普通内存注册为页锁定 / 解除页锁定），对已经用 malloc 分配好的普通内存，后续再锁定

影响与特性：

  • 页锁定内存本质上不再属于主机可分页虚拟内存，操作系统不会把这块内存交换到 swap 磁盘

pageable memory（可分页内存）

  • 物理内存（RAM）：电脑里的内存条，读写极快，但容量有限。

  • Swap（交换分区）：硬盘上专门划出的一块区域，速度比内存慢几百倍，用来救急。

  • 内存页 page：操作系统管理内存的最小单位（一般 4KB 一页）。OS 不是按单个字节管理内存，而是一页一页管理。

  • 当你用 malloc/new 分配内存，拿到的是虚拟内存地址，不是直接的物理内存条地址。OS 维护一张映射表：虚拟地址 ↔ 物理内存页。

虚拟内存机制

操作系统给进程分配的是虚拟地址，不是直接物理内存。
OS 可以在内存紧张的时候，把这块内存对应的页面 swap 交换到磁盘交换区；需要的时候再加载回物理内存。
这就是「可分页」。

malloc/new 只是标准 C/C++ 内存分配接口

它们调用操作系统原生内存分配（mmap / VirtualAlloc），不会去调用 CUDA 驱动做页锁定，所以分配出来的内存页面默认是可以被 swap 换出的。

Swap out（页面换出）

内存紧张时，发生 Swap out（页面换出）
  • 场景：你的程序、浏览器、CUDA 程序一起跑，所有程序需要的内存总和 > 物理内存条大小。
    操作系统会做一件事：
  1. 挑一块暂时不用的内存页面（比如你 malloc 出来的一块数组）；
  2. 把这一页里的数据，写入硬盘的 Swap 分区保存；
  3. 释放这块物理内存条空间，给别的正在运行的程序使用；
  4. 虚拟地址仍然保留，但对应的物理内存现在是空的，数据在硬盘里。
程序再次访问这块内存：Swap in（页面换入）

当你的代码再次读取这个 malloc 数组时：

  1. CPU 发现：这个虚拟页不在物理内存；
  2. OS 触发缺页中断；
  3. 从硬盘 Swap 分区，把这一页数据重新读回到物理内存条；
  4. 程序才可以正常读取数据。

硬盘速度很慢，频繁 swap 会造成系统卡顿。

为什么这件事会影响 CUDA 传输？

GPU 的 DMA 直接访问物理内存，它看不懂虚拟地址，不能等待操作系统从硬盘把页面读回来。

  • 如果是普通 pageable 内存：传输中途，页面可能被换到硬盘。GPU DMA 直接读就会失败。
  • 所以 CUDA 在cudaMemcpy时，只能额外开辟一份临时 pinned 主机缓冲区：先 CPU 拷贝到不会被 swap 的缓冲区，再传给 GPU。
  • Pinned 内存：告诉操作系统：这一页绝对不许换去 Swap，必须永久留在物理内存条中。OS 不能把它换出硬盘。所以 GPU DMA 可以直接访问，支持异步拷贝。
DMA(Direct Memory Access，直接内存访问)

GPU 的 DMA 传输，只能直接读物理内存条里的数据，不能直接读硬盘。

1. 没有 DMA（CPU 搬运）

假设要把主机内存的数据传给 GPU：

  1. CPU 读内存里的数据
  2. CPU 把数据一点点送到 PCIe 总线
  3. 写到 GPU 显存
    👉 CPU 全程被占用，只能干搬运这件事，没法同时做别的计算。
2. 有 DMA（硬件搬运）

DMA 控制器是一个独立硬件。流程变成：

  1. CPU 只需要下达一条指令：把 A 地址的数据搬到 B 地址
  2. 剩下的数据搬运工作由 DMA 硬件独立完成，CPU 解放出来，可以去跑别的代码
  3. 搬运结束后，DMA 发中断通知 CPU：传输完成了

核心：数据不经过 CPU 寄存器中转，内存 ↔ 外设直接传输。
GPU、网卡、硬盘控制器都带有 DMA。在 CUDA 里，就是 GPU 通过 PCIe 上的 DMA，完成主机内存 ↔ GPU 显存的数据传输。

CUDA STREAMS(cuda流)

默认API

  • Kernel launches相对于 CPU 是异步的(CPU 调用kernel<<<>>>提交内核后，不会阻塞，CPU 线程直接继续往下跑，不用等 GPU 内核跑完。)
  • 普通cudaMemcpy（设备→主机、主机→设备）阻塞 CPU 线程(CPU 调用这个函数后，原地等待，直到整个内存拷贝全部完成，代码才继续往下执行)
  • 驱动会串行执行 CUDA 调用（传统默认流），所有任务都放到同一个默认流里，任务排队串行执行：前一个任务做完，才跑下一个。默认流无法实现拷贝和计算重叠。

流和异步API

  • cudaMemcpyAsync(D2H, H2D)异步拷贝，不会阻塞 CPU：CPU 提交拷贝任务之后，函数立刻返回，CPU 继续跑自己的代码，不用等传输结束。✅ 使用前提：主机内存必须是 Pinned 页锁定内存。

  • 可以让内核计算 + 内存拷贝并发执行（Copy-Compute Overlap，拷贝计算重叠）

  • 大多数 GPU 支持双向同时传输：H2D（主机→GPU）和 D2H（GPU→主机）可以并行跑。

Stream 的定义

  • CUDA 流 = 在 GPU 上严格按提交顺序执行的一系列操作，同一个流内部：任务必须串行，按你提交的顺序依次执行，不能乱序。

  • 不同流的操作，可以交错执行(流 A 的任务 和 流 B 的任务，GPU 可以交替执行)

  • 来自不同流的内核计算和内存拷贝，可以并行重叠执行

SM（Streaming Multiprocessor）

  • 流式多处理器

CUDA 流的核心规则

  • 同一条流里提交的 2 个操作：严格按提交顺序串行执行（同流串行）

  • 不同流提交的操作：CUDA 不规定任何顺序，无默认依赖

  • Operation（操作）定义：

    • cudaMemcpyAsync 异步内存拷贝；
    • Kernel 内核调用（kernel<<<grid,block,0,stream>>>）
      所有带 stream 参数的 CUDA API，还有流回调函数，都算作流操作。

提醒

  • 不带 stream 参数的 API（cudaMemcpy、cudaMalloc等）不属于自定义流操作，大多走默认流，容易带来隐式同步，破坏并发。
  • stream 参数只是提交任务时标记归属哪条流；不是等待流完成。提交之后 CPU 立刻继续跑，是异步。
  • 想要等待流全部任务结束，调用：cudaStreamSynchronize(stream)。

流创建与拷贝/计算重叠

实现拷贝计算重叠的必要条件

  • 主机 ↔ GPU 的异步拷贝，主机侧内存必须是 Pinned 页锁定内存

  • Kernel内核和memcopy，放到不同的、非 0 的自定义流

  • 是可能重叠，不是一定重叠，根据资源情况定

Warp（线程束）
  • Warp 是 NVIDIA GPU 硬件上 SM 内部最小调度执行单位，1 个 warp 固定包含 32 个线程，编号 0~31，叫 lane(通道)，采用 SIMT（单指令多线程）模型执行。
  • Block 会被切分成多个 warp，warp 不会跨 Block！Block 的边界可以落在 warp 中间。
SIMT 单指令多线程

同一个 warp 里 32 个线程同一时刻执行同一条指令，但每个线程拥有自己独立寄存器、独立 PC 程序计数器、私有数据。

  • SIMD：向量硬件，所有线程共用 PC；
  • SIMT：允许 warp 内线程独立分支，硬件通过掩码 mask 关掉不走该分支的线程。
Warp 调度与延迟隐藏

SM 里有 warp 调度器（warp scheduler），管理一批就绪 warp：

  • 如果某个 warp停顿：比如访问 Global Memory、发生 Unified Memory 缺页、等待内存，只有这个 warp 暂停；
  • SM 立刻切换去执行其他就绪 warp；
  • warp 切换是零硬件开销，GPU 靠大量 warp 并行，把内存访问延迟隐藏掉。
Warp Divergence 分支发散

同一个 warp 内部，线程走不同 if/else 分支，就叫 warp divergence。

  • GPU 会串行依次执行每一条分支；不走这条分支的线程被 mask 屏蔽，不做计算；
  • 并行度下降，性能变差；

例子：warp 中偶数 thread 进 if，奇数 thread 进 else。GPU 先跑 if（奇数 mask 关闭），再跑 else（偶数 mask 关闭），原本 1 次并行变成 2 次。
⚠️ 注意：不同 warp 之间分支互不影响，不会发散，发散只发生在同一个 warp 内部。

Occupancy（占用率）

  • Occupancy（SM 占用率） =当前 SM 上驻留的活跃 warp 数量 / SM 硬件最大可支持 warp 总数

  • 每个线程寄存器越多 → SM 能容纳的总线程 /warp 越少 → occupancy 下降

  • SM 寄存器堆是共享资源；单线程寄存器越多，SM 上能放的总 warp 越少，occupancy 降低。

Register 寄存器
  • 单个线程私有，位于SM片上,每个线程可以有多个寄存器，不是一个线程只有一个寄存器
  • 寄存器溢出：如果编译器发现需要的寄存器 > 当前可用硬件寄存器：
    • 溢出（spill）：把一部分变量压到 Local Memory（属于 Global Memory 的一部分）。
    • 性能严重下降
  • 现代 GPU 硬件上限：每个线程最多 255 个 32bit 寄存器，由编译器自动分配
shared memory(共享内存)

SM私有，block内共享

  • 每个 SM，硬件上只有 1 片统一的片上 SRAM 内存池（Shared Memory / L1 统一缓存），不是多个独立 shared memory 硬件模块。这块内存池，会动态切分，分配给当前驻留在这个 SM 上的多个线程块（block）使用。
L1 Cache

  • L1 Cache 在每个 SM 内部（片上 on-chip），每个 SM 独立拥有自己的 L1/Shared 存储池；不同 SM 之间 L1 不互通。

  • 每个 SM 拥有一块统一片上 SRAM，资源可以在 Shared Memory 和 L1 Cache 之间调配；分配给 Shared 的部分不能用作 L1，反之亦然。Shared Memory 由程序员控制，L1 Cache 是硬件自动缓存。

Global Memory 全局显存
  • 所有线程都能访问，位于板载显存
L2 Cache
  • L2 Cache 是 GPU 芯片上，被所有 SM 统一共享的片上缓存，不属于某个单独 SM；不能当作 Shared Memory 使用。
  • L2 在 L1 Cache 和 Global Memory（显存）之间，起到全局数据缓存、合并内存请求的作用。
  • 完全硬件管理，不可切分
总结
  1. Register 寄存器：单线程私有，最快，容量极小
  2. Shared Memory：SM 片上，block 私有，程序员控制；与 L1 共用 SRAM 池
  3. L1 Cache：SM 片上，硬件自动缓存
  4. L2 Cache：全 GPU 共享片上缓存
  5. Global Memory（显存）：板载 DRAM，容量最大，速度最慢

DEFAULT STREAM 默认流

  • 不指定 stream、或者 stream 参数写 0，就是使用默认流（legacy 默认流）；它是特殊流，会和所有其他自定义流之间产生隐式全局同步，非常容易破坏多流并行！

  • 什么时候使用默认流：

    • kernel 不写<<<grid,block>>>第 4 个流参数，等价于stream=0
    • cudaMemcpy()（不带 stream 的阻塞拷贝函数）底层就是提交到默认流
    • cudaMemcpyAsync(..., 0)，指定 stream=0，同样是默认流

  • 传统默认流行为：

    • 默认流里面任务开始前：之前所有已经提交到 GPU 的任务（所有自定义流 stream1、stream2）必须全部执行完成，默认流任务才能启动。
    • 默认流任务执行期间，后面提交给其他流的任务，必须等待默认流任务执行完，才能开始运行。

  • 修改默认流行为：per-thread 默认流

    编译选项：
    nvcc --default-stream per-thread

    开启后：

    • 默认流不再是全局同步的特殊流，变成普通的常规流
    • Each host thread will get its own “ordinary” default stream
      每个 CPU 主机线程拥有独立的默认流，流之间不再有全局隐式同步，可以正常并行。

    -用nvcc --default-stream per-thread可以把默认流变成普通流，每个 host 线程独立默认流，消除全局隐式同步。

cudaLaunchHostFunc () —— Stream 回调（Host 回调函数）

把一段 CPU 主机函数，插入 CUDA 流的任务队列。等这个流前面所有 GPU 任务全部执行完毕之后，自动执行这个主机回调函数。
旧 API cudaStreamAddCallback() 已经废弃，现在用 cudaLaunchHostFunc()。

  • 可以定义一个主机端 CPU 函数，把这个函数作为一个任务，放进 CUDA 流队列。(流队列里可以放三类任务：cudaMemcpyAsync、kernel 启动、host 主机回调。)
  • 遵守流语义：流是串行队列，回调函数必须等到该流前面所有任务全部执行完成，才会触发执行。
  • 回调函数不是在你自己的 CPU 主线程执行，而是由 GPU 驱动单独创建的驱动线程来跑这个主机函数。
  • 最重要限制：回调函数内部不能调用任何 CUDA Runtime API，也不能启动 kernel！
    • 禁止：cudaMalloc / cudaMemcpy / cudaStreamSynchronize / 启动核函数
    • 原因：驱动线程环境不支持 CUDA Runtime，调用会出错死锁。
    • 回调里面只能写普通 CPU 逻辑：比如标记任务完成、设置 flag、通知别的线程、日志打印。
    • 适用场景：延迟 CPU 工作，等 GPU 计算结果就绪之后，再执行 CPU 后续处理。
    • 新代码统一使用cudaLaunchHostFunc()这个新API

统一内存（Managed Memory）下的拷贝计算重叠（按需分页 demand-paging）

Managed Memory = Unified Memory 统一内存，由cudaMallocManaged()分配，CPU/GPU 共用一套虚拟地址；底层按需分页 demand-paging。

  • 整体流水线思路和普通多流拷贝计算重叠一样；
    区别：不用cudaMemcpyAsync显式拷贝，改用 cudaMemPrefetchAsync() 预取统一内存页面。
    • cudaMemPrefetchAsync：异步地把统一内存的数据页面迁移到指定设备（GPU/CPU），放到流中执行。
  • 遵守流语义：页面迁移（内存搬迁）会按照流队列顺序执行，保证先后次序。
    • 放在同一个流里：prefetch → kernel，一定等页面迁移完成，kernel 才启动。
  • cudaMemPrefetchAsync比普通cudaMemcpyAsync工作量更大：它不只是搬数据，还要更新 CPU、GPU 两端的页表（page table）。
    • cudaMemcpyAsync：单纯数据拷贝，地址是独立的 host/device 内存
    • cudaMemPrefetchAsync：数据拷贝 + 修改两边页表映射关系
  • 这个函数主机端函数返回会慢很多（不是指 GPU 任务，是 host 调用这个 API 本身），会在时序上引入意料之外的空隙，破坏拷贝计算重叠。
    • ⚠️ 普通 async 函数：入队后立刻返回；
      cudaMemPrefetchAsync 因为要操作页表，host 侧开销大，阻塞主机线程一段时间，流水线出现空档。
  • 繁忙流 (busy stream) 和空闲流 (idle stream) 行为不一样。反直觉结论：负载满的 busy 流，吞吐反而更好。
    • 简单理解：流队列已经有很多任务时，驱动可以把页表更新、页面迁移和已有任务调度重叠；空闲流下 prefetch 的页表开销更容易暴露出来，拖慢性能。

统一内存是什么

统一内存 = CPU 与 GPU 共享同一套虚拟地址空间，同一个指针，CPU、GPU 都可以读写，底层页面会自动在主机内存和 GPU 显存之间迁移。

  • 核心原理：按需分页 demand-paging（Pascal 架构之后）
    1. 刚分配内存时，页面不一定在 CPU 或 GPU；
    2. CPU/GPU 第一次访问这个内存，如果页面不在当前设备 → 触发缺页 fault；
    3. CUDA 运行时自动把对应的内存页面迁移过来，然后继续执行；

这个自动迁移就叫 demand-paging 按需分页。

  • 两个关键 API

    1. cudaMemPrefetchAsync()
      主动预取页面，提前把页面迁移到 GPU（或 CPU），放到流里异步执行，避免 kernel 运行时发生缺页，缺页会造成巨大延迟，性能下降，尤其是当大量页面并发缺页，触发 fault 的那个 warp 暂停等待 PCIe 传输。

    做 copy-compute overlap 时，用它替代cudaMemcpyAsync。
    缺点：不仅搬数据，还要更新 CPU 和 GPU 两端页表，host 调用开销更大，容易产生流水线间隙。

    1. cudaMemAdvise()：给驱动提示内存访问模式（比如数据主要给 GPU 读），辅助优化页面迁移策略。

  • 优点

    1. 简化代码：省去大量cudaMemcpy，不用管理 host、device 两块内存。
    2. 支持显存超订阅（oversubscription）：数据集大小 > GPU 物理显存。GPU 需要的时候，页面自动从系统内存换入换出，可以跑超出显存容量的任务。
    3. 同一个指针，CPU/GPU 都能访问，写代码更直观。

cudaEvent 事件

cudaEvent 是可以放到流队列里的标记 marker；跟着流顺序执行，流跑到这个 event 位置时，event 完成。两大用途：GPU 计时、流之间同步。

  • cudaEvent 是一个标记，插入 CUDA 流的任务队列，和 kernel、cudaMemcpyAsync 一样排队。
  • 调用cudaEventRecord()，就是把这个事件标记提交（record 录制）进流，只是入队，不是立刻记录时间。
  • 等流执行一路跑到这个 marker 位置，GPU 才真正打上时间戳 → event completed（完成）。（> 流语义：流前面所有任务执行完，才触发这个 event。）
  • 最常用：给 GPU 设备任务计时（kernel、异步拷贝耗时）

  • 除计时外，还可以做跨流同步：

    • 比如 streamA 提交 event；streamB 调用cudaStreamWaitEvent()，让 streamB 等待这个 event 完成之后，才执行后面任务。用来搭建复杂多流并发流水线。

  • event 记录的是GPU 设备任务时间，不统计 CPU 主机代码耗时；复杂多流并发场景下，计时结果容易不符合预期。

Multi-GPU 多 GPU 设备管理

  • CUDA 多设备管理 API 只是底层 GPU 控制接口，不是并行编程框架。多 GPU 大规模并行，通常还是要搭配 MPI；OpenMP 用于 CPU 多线程。

  • 程序查询、选择 GPU

    • cudaGetDeviceCount(int *count)：查询本机一共有多少块可用 GPU，结果存入 count。
    • cudaSetDevice(int device)：设置当前线程的活动 GPU（当前设备）。

      后续cudaMalloc、kernel 启动、流创建等 CUDA 操作，默认都作用在这个 device 上。

    • cudaGetDevice(int *device)：查询当前线程正在使用哪一块 GPU，设备号写入 device。
    • cudaGetDeviceProperties(cudaDeviceProp *prop, int device)：获取指定 GPU 的硬件信息（SM 数量、显存大小、warp 特性等）。

  • 多个 CPU 主机线程，可以共享同一张 GPU。多个 host 线程往同一个 GPU 提交任务（kernel、拷贝），驱动负责调度。

  • 单个 CPU 主线程，可以管理多张 GPU

    • 使用 cudaSetDevice(i) 在不同 GPU 之间来回切换当前设备。
    • cudaMemcpyPeerAsync(...)：GPU 点对点异步拷贝（Peer-to-Peer），直接在两张 GPU 显存之间传输数据，不需要经过主机内存。前提：硬件开启 P2P 访问支持。

P2P

  • Peer-to-Peer，GPU 点对点访问
  • 支持 P2P 的多张 GPU，可以直接访问对方显存，数据传输不需要经过 CPU 主机内存

MPI

MPI 是一套跨节点并行编程标准，基于「消息传递」，用来在多台服务器 / 多个进程之间收发数据；常用于大规模集群、多机多 GPU 场景，它不是 CUDA 的一部分。

  • MPI 采用进程并行：启动很多独立进程（MPI rank）

    • 每个 rank 是独立操作系统进程，有独立地址空间
    • 进程之间不能直接访问对方内存，只能显式发送、接收消息来交换数据
    • rank 可以跑在同一台机器，也可以分布在不同服务器节点
    • MPI只负责进程间通信，不做 GPU 计算；GPU 计算仍然交给 CUDA kernel。

    和线程（OpenMP）对比：

    • OpenMP：共享内存，一台机器内，多线程共用同一块内存；
    • MPI：分布式内存，进程内存互相隔离，靠消息传数据。
  1. 单机多 GPU：只用 CUDA Runtime（cudaSetDevice、P2P）就能管理；
  2. 多机多 GPU（跨服务器）：CUDA P2P 只能单机内，跨机器显存不能直接访问 → 必须 MPI。

经典组合：MPI + CUDA
每台服务器上启动 1 个 MPI 进程，进程绑定本机一张 GPU；MPI 负责服务器之间的数据交换，CUDA 负责本 GPU 内部计算。

  • 常用API:

    • MPI_Init()：初始化 MPI 环境
    • MPI_Comm_rank()：获取当前进程编号 rank
    • MPI_Comm_size()：获取总共有多少 MPI 进程
    • MPI_Send()：发送消息
    • MPI_Recv()：接收消息
    • MPI_Finalize()：结束 MPI

OpenMP

OpenMP 是共享内存并行编程标准，用于单机内 CPU 多核并行；基于多线程，多个线程共享同一块主机内存，通过编译制导指令#pragma omp开启并行。(所有 OpenMP 线程在同一个进程内，共享进程全局内存；线程之间可以直接读写同一块变量)

  • 和 MPI、CUDA 的定位区分：

    • OpenMP：单机 CPU 多核，共享内存、多线程
    • MPI：多进程，分布式内存，跨服务器集群
    • CUDA：GPU 并行（设备端 SIMT 线程）

  • OpenMP 采用Fork-Join（分支 - 归并）模型

    1. 程序一开始只有主线程运行；
    2. 遇到#pragma omp parallel，主线程 fork，生成一组子线程；
    3. 多个线程并行执行任务；
    4. 并行区域结束，所有子线程合并（join），回到单主线程继续往下跑。

CUDA Runtime（CUDA 运行时 API）

  • CUDA Runtime 是高层主机端 C/C++ 库，封装底层 CUDA Driver API；提供一系列cudaXXX开头函数，用来管理 GPU、显存、流、事件，并且支持Kernel<<<grid, block>>>这种核函数启动语法。

  • 区分：底层叫 CUDA Driver API（函数前缀cuXXX），Runtime 是建立在 Driver 之上的高层封装。

  1. 执行位置：Host（CPU 主机端）
    所有cudaXXX()函数都在 CPU 上执行，不能在 GPU kernel 内部调用 Runtime 函数。作用是向 GPU 提交任务、管理 GPU 资源。
  2. 自动初始化
    Runtime 在第一次调用 cuda 函数时自动初始化 CUDA 环境，不需要手动初始化；
    Driver API 必须手动调用cuInit()初始化。
  3. 提供的功能（就是前面学的）
  • 设备管理：cudaGetDeviceCount、cudaSetDevice、cudaGetDeviceProperties
  • 内存管理：cudaMalloc、cudaFree、cudaMallocManaged统一内存、cudaMemcpy、cudaMemcpyPeerAsync
  • 流与事件：cudaStreamCreate、cudaEventCreate、cudaEventRecord，用于 GPU 计时、异步同步
  • 启动 kernel：kernel<<<grid,block>>> 这个三角括号语法，依赖 Runtime 实现

Multi-GPU - Streams（多 GPU 下的 CUDA 流）

流（stream）和 cudaEvent 在创建的时候，就自动绑定到当前cudaSetDevice选中的 GPU 设备；不同 GPU 的流可以通过 event 实现跨设备同步，不同 GPU 上的 kernel 可以并发执行。

  • 流和 cudaEvent 会隐式自动绑定设备
    当你调用cudaStreamCreate / cudaEventCreate时，当前cudaSetDevice选中的设备，就是这个流 / 事件永久绑定的 GPU。流一旦创建，所属设备不能更改。

  • 每一块 GPU，都拥有独立的默认流（default stream）

  • 如果向一个不属于当前设备的流提交 kernel，启动会失败！

  • cudaStreamWaitEvent()：可以实现跨设备流同步！,例如：GPU1 的流等待 GPU0 上记录的 event。即使 event 在别的 GPU，也能做设备间同步。

  • cudaEventQuery()：非阻塞查询，检查 event 是否已经完成（不会卡住 CPU）。

Multi-GPU：Device-to-Device 设备间数据拷贝（P2P/GPUDirect）

如果硬件拓扑支持，GPU 之间可以通过 PCIe/NVLink 直接传输显存数据，不走主机内存；需要先建立双向 Peer 对等关系，之后用cudaMemcpyPeerAsync完成 P2P 异步拷贝，也就是 GPUDirect P2P。

  • 系统硬件拓扑支持时，GPU 之间可以通过 PCIe 或者 NVLink 高速互联，直接把显存数据从一张 GPU 传到另一张。(NVLink 是 NVIDIA 更高带宽的专用互联，比 PCIe 速度更快)

  • 设备必须显式建立 peer 对等关系（称为 clique 对等组），P2P 才可以生效，不是默认开启。

  • 如果双向都要互相访问，两个方向都要分别 enable：

    • 开启 GPU0 可以访问 GPU1
    • 开启 GPU1 可以访问 GPU0
      只开单向，只能单向拷贝。

  • 建立 P2P 之后，两张 GPU 之间拷贝不再需要经过主机系统内存做中转，这就是 GPUDirect P2P 传输。

  • 无 P2P 时：GPU0 → Host 内存 → GPU1（两次 PCIe 传输）

  • 有 P2P 时：GPU0 ↔ GPU1，直接传输，绕过主机内存。

cudaDeviceEnablePeerAccess(peerDevice, flags)

第一个参数：你想要访问的那个对端设备号；第二个参数永远传 0（flags，保留参数，目前没有其他选项）

  • 对等组clique内，可同时建立 P2P 连接的 GPU 数量有硬件上限，不能无限多卡全部互相 P2P。

其它并发场景

CUDA 有两种典型并发：Host/Device 并发（CPU 主机代码 和 GPU 核函数重叠执行）；同卡多 Kernel 并发（同一个 GPU 上，多个不同流的 kernel 同时跑）

  • Host / Device execution concurrency 主机 / 设备并发
  • Concurrent kernels 同设备多 Kernel 并发（同一个 GPU 上多个 kernel 并行）
  • 实际开发里，在同一块 GPU 上看到多个 kernel 同时跑并不容易。
  • 要求 kernel 占用寄存器、共享内存等硬件资源少，并且执行时间足够长。
  • 单块 GPU 能够同时并发执行的 kernel 数量存在硬件上限，不能无限并发。
  • 多个 kernel 并发的效率，不如用一个大 kernel 把 GPU 硬件占满。GPU 的设计思路：尽量单 kernel 充分利用全部 SM。

CUDA 流优先级

CUDA 流可以设置优先级，只对并发执行的 Kernel 生效；GPU 调度器会优先调度高优先级流里的线程块；当前硬件一般只有高低 2 档优先级，不支持抢占（block 一旦开始执行就不能被打断）。

  • CUDA 流支持可选地定义优先级。创建流的时候，可以指定优先级。
  • 流优先级只影响并发运行的 kernel(如果两个 kernel 不是并发（串行排队执行），流优先级不起任何作用。只有多个 kernel 同时在 GPU 上跑的时候，优先级才生效。)
  • GPU 的 Block 调度器，会尽量优先调度高优先级流中的线程块，再调度低优先级流的 Block。
  • 当前硬件实现一般只提供2 档优先级：高、低。
  • 不支持 Block 抢占！

含义：一个 block 一旦在 SM 上启动运行，就不会被高优先级任务打断。
优先级只能影响还没开始调度的 block；已经跑起来的 block 会一直执行完成。

CUDA Graphs 概述（CUDA 图)

CUDA Graph 是 CUDA10 引入的特性，把一系列 GPU 任务（kernel、内存拷贝等）组织成有依赖关系的图结构，提前一次性构建好，之后可以反复提交到流上执行，减少 CPU 反复提交任务的开销。

  • CUDA 10 版本新增功能。

  • 可以定义流上的一系列任务：核函数、内存拷贝、回调、主机函数，甚至可以嵌套子图。

  • 每一项任务，都是图里的节点 node。

  • 可以定义节点之间的依赖关系，例如：3 个节点全部完成之后，下一个节点才允许开始执行。

  • 任务依赖关系，对应图的边 edge。

  • 图一旦构建完成，把整个图一次性提交到流中执行。

  • 构建好的图可以重复多次执行，适合循环执行固定任务序列（深度学习推理就是典型场景）。

  • 两种创建图的方式：

    • 手动构建（manual）：逐个创建 node、手动添加依赖边
    • 捕获模式（stream capture）：直接捕获一段流里提交的任务，自动生成 graph（更常用）
