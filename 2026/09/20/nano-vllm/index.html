nano-vllm

发表于 2026-09-20 更新于 2026-09-23 分类于 ai infra

第一优先级（必学，面试高频，你现在正在看的）

1. Sequence、Scheduler 调度器（你刚读的这一大段代码）

这是推理引擎的任务管理层

  • Sequence：一条请求的完整生命周期封装（prompt token、已生成 token、状态、block_table、采样参数）
  • Scheduler 两个队列：waiting（待 Prefill） / running（Decode 中）
  • 调度策略：Prefill 优先；Prefill 按总 token 数限制 batch、Decode 按序列数限制 batch
  • Chunked Prefill：长 Prompt 分片 prefill
  • 抢占 Preempt：显存不足时踢出 running 里的序列，释放 KV，后面重跑 prefill
  • postprocess：模型跑完之后更新 seq 状态、判断 EOS、回收 KV block

面试常问：连续批（Continuous Batching）原理；prefill/decode 为什么 batch 约束不一样；抢占机制；chunked prefill 解决什么问题。

2. BlockManager + PagedAttention（核心中的核心）

vLLM 最标志性技术，也是 AI Infra 必考

  • KV Cache 不再是连续大数组，拆成固定大小 Block（页）；block 里面存若干 token 的 K/V
  • block_table：每个 seq 维护一张页表，记录该序列用到哪些 block，对应你前面看到的 block_tensors
  • block 分配、释放、引用计数
  • Prefix Cache（hash_blocks）：KV block 哈希，相同前缀请求共享 KV，减少显存与 prefill 计算
  • 理解 slot_mapping：把逻辑 token 位置映射到 GPU 显存物理 block+slot，是 PagedAttention 算子寻址关键

3. Prefill 和 Decode 两套数据流（prepare_prefill /prepare_decode）

理解两个阶段的差异，这是 LLM 推理最基础的分水岭

  • Prefill：一次性处理 prompt 全部 token，并行计算 KV；输入二维
  • Decode：每次仅输入 1 个新 token，自回归生成；输入一维
  • prepare_prefill：构造 cu_seqlens /cu_seqlens_q/cu_seqlens_k，用cu_seqlens变长标识
  • prepare_decode：context_lens，block_tables，slot_mapping
  • set_context /get_context：给 CUDA Graph 准备全局上下文

4. CUDA Graph 捕获与重放（capture_cudagraph /graph.replay）

推理性能优化重点，你前面看的capture_cudagraph

  • 什么时候捕获 graph：初始化阶段，提前录制 decode 计算流
  • 约束：tensor 底层显存地址不能变，只能原地改写（切片赋值），不能新建 tensor
  • graph_vars：预分配好的显存缓冲区，每次 replay 前原地写入新数据
  • 适用场景：Decode 阶段（计算图固定）；Prefill 不适合 CUDA Graph（输入长度变化）

面试问：CUDA Graph 原理、优缺点；为什么 prefill 一般不用 cuda graph；原地赋值的必要性。

✅ 第二优先级（算子、模型层、性能统计）

  1. 模型前向 + PagedAttention 自定义算子
    看模型怎么调用 PagedAttention，理解：输入 input_ids、positions、block_tables、slot_mapping、context_lens 怎么传入 Attention 算子。
    区分：标准 Self-Attention 和 PagedAttention 的区别。
  2. Sampler 采样器

  4. 性能指标统计

预热（Warmup）调用

在正式压测之前，跑一次轻量推理，提前触发所有一次性初始化工作：

  1. 模型权重加载：把模型参数从 CPU 内存拷贝到 GPU 显存；
  2. CUDA 环境初始化、CUDA Graph 捕获
    CUDA Graph 会提前捕获计算流，后续正式推理直接重放 graph 提速。Graph 捕获只会在第一次推理触发；如果不预热，捕获耗时会算进 benchmark 计时，吞吐结果虚低。
  3. GPU 显存初始化、显存池 / Page 池预分配：nano-vllm 的 PagedAttention 的 KV Cache 页内存池，第一次运行时才会分配；
  4. 内核编译（torch.compile/ Triton kernel JIT 编译）：第一次运行自定义算子会触发即时编译，编译开销很大，只发生首次执行。
  5. 初始化内部调度器、请求队列、后台线程。

所有上面这些操作只执行一次。预热跑完之后，后面正式llm.generate()就不会再产生这些一次性开销，测出来的时间才纯粹是推理计算耗时。

这是 nano-vLLM 的 LLMEngine 主引擎类，是整套推理框架的入口，负责：

  1. 初始化张量并行多进程（TP，tensor parallel）
  2. 创建调度器 Scheduler、模型执行器 ModelRunner

多进程启动方式spawn

ctx = mp.get_context("spawn")

spawn 工作原理

  • fork：复制父进程的内存空间（拷贝内存页），子进程一创建就拥有父进程所有变量、打开的文件、CUDA 上下文。(cpu适用)
  • spawn：
    1. 新建一个全新 Python 解释器进程
    2. 重新import 所有模块，从头执行代码
    3. 只把你显式传给 Process(args=...) 的参数，序列化（pickle）传递给子进程
    4. 子进程执行 target 函数

重点：spawn 不会继承父进程内存、变量、CUDA 上下文！
父进程里定义的变量，子进程默认看不到；只有通过 args 传过去的数据才会存在
nano-vLLM 这里选 spawn，核心原因：CUDA + GPU 场景不能用 fork。

优点（GPU 场景最关键）

  1. 安全支持 CUDA
    fork 会直接复制父进程 CUDA 上下文，子进程使用 GPU 会直接崩溃、出现 CUDA 错误。
    spawn 新开解释器，每个进程独立 CUDA 上下文，多 GPU 张量并行 TP 必须用 spawn。
  2. 干净隔离，进程之间内存完全独立，不容易出现内存脏数据、锁冲突。

缺点

  1. 启动慢：子进程要重新 import 全部模块、重新加载模型。nano-vllm 中每个 TP 子进程都会单独加载模型分片。
  2. 传参限制：传给子进程的 args 里的对象必须支持 pickle 序列化。像 GPU 张量、打开的文件句柄不能直接传

ModelRunner

张量并行 TP 子进程执行单元

核心架构一句话：rank0 既是调度者，也是模型 worker；rank>1 的 TP 子进程是纯模型 worker，没有调度能力，只会阻塞等待 rank0 通过【共享内存 SharedMemory + Event 信号灯】下发任务；NCCL 负责模型张量并行的 GPU 间集合通信。

torch.distributed

torch.distributed 是 PyTorch 自带分布式通信库，用来做多卡分布式训练 / 推理通信，底层可以绑定 NCCL/Gloo 等后端。

初始化 pytorch 分布式进程组

  • backend=nccl：GPU 之间通信用 NCCL，张量并行必备
  • tcp://localhost:2333：主节点地址端口，所有 TP 进程通过这个地址握手组网
  • world_size：TP 总卡数；rank 当前编号

NCCL(NVIDIA Collective Communications Library)

NVIDIA 集合通信库，专门给多 GPU 之间高速集合通信设计，是大模型张量并行 / 流水线并行的底层通信库,专门实现 GPU 集合通信算子。

  • allreduce（张量并行最常用，TP 做 Attention、MLP 时，多张卡求和归并结果）
  • allgather
  • broadcast
  • reduce
  • reduce_scatter

张量并行 TP 原理：一层矩阵切分到多张 GPU 分别计算，计算完allreduce把所有卡的结果求和，同步到每一张卡。这个 GPU 之间的数据传输就是 NCCL 完成。

  1. 直接 GPU ↔ GPU 通信，不走 CPU 内存
    数据直接从一张 GPU 显存拷贝到另一张 GPU 显存，绕过主机内存，速度远高于 Gloo（走 CPU 内存的通信后端）。
  2. 自动感知硬件链路：PCIe / NVLink。
    如果 GPU 之间有 NVLink，NCCL 会自动优先走 NVLink，带宽更高、延迟更低。
  3. 多进程、多节点都支持：单机多卡，或者多机器分布式都能用。
  4. 和 PyTorch 深度集成，torch.distributed指定backend="nccl"就启用。

大模型推理里的采样（Sampling）

大模型推理时每一步输出词表上的概率分布，采样就是从该分布选择下一个 token 的过程。
如果只用贪心取最大概率，生成内容容易单调、重复。采样通过 temperature、top_p、top_k 等参数，控制随机性，在保证通顺的前提下调节生成多样性。采样仅用于自回归推理，训练不需要采样。

1. 采样是什么？

大模型每一步输出，不是直接输出一个 token，而是输出一个概率分布（logits）：也就是下一个位置所有词表 token 各自的概率。
采样，就是从这个概率分布里，选出下一个 token 的过程。

简单一句话：

模型给出一堆候选词 + 各自概率，采样就是按规则挑出下一个词。

2. 为什么必须采样？

如果不采样，最简单做法就是直接选概率最大的 token → 叫Greedy（贪心解码），贪心其实也算一种特殊采样。
但纯贪心有明显缺点：

  1. 容易重复、呆板、局部最优，句子容易卡住循环，生成多样性很差；
  2. 没有办法控制生成随机性，写文案、聊天、创作场景不适用。

采样提供一套可配置策略，目标：
✅ 在生成质量和多样性之间做权衡。
通过SamplingParams里这些参数控制采样行为：

  • temperature 温度：调节分布平滑度；越高越随机，越低越接近贪心
  • top_p（nucleus sampling）：只取概率累积到 p 的一小部分候选词
  • top_k：只保留概率最高的 k 个 token
  • ignore_eos：是否忽略结束符，强制继续生成，你代码里就有这个参数

3. 两种典型采样（面试常问）

  1. Greedy 贪心采样：永远取概率最大 token，确定性输出，适合代码 / 数学推理，几乎无随机。
  2. 随机采样（带 top-p/top-k/temp）：按概率随机抽取，高概率词更容易被选中，但有机会选次优 token，适合对话、写作。

注意：训练阶段用的是 teacher forcing，不需要采样；采样只发生在自回归推理 decode 阶段（prefill 之后逐 token 生成）。

top_k

只保留概率最高的 k 个 token，剩下所有 token 概率直接置 0，再重新归一化采样。

top_p（核采样，nucleus sampling）

保留最小的候选集合，使得这些 token 概率累加 ≥ p，其余全部丢弃，再归一化采样。
不是固定个数，是按概率总和动态筛选候选词。

三者执行顺序：

  1. logits 除以 temperature
  2. 做 top_k 截断（去掉 k 名以外 token）
  3. 做 top_p 核截断（去掉尾部低概率 token）
  4. softmax 归一化
  5. 随机采样选出下一个 token

temperature 温度

缩放概率分布，控制随机程度

warmup_model

在正式接收用户请求前，提前跑一次推理，触发 torch.compile 的编译、CUDA 内核加载、显存预分配，避免第一条真实请求很慢（编译延迟）。

run

run 是 ModelRunner 单步推理入口。根据 is_prefill 标记，分别调用 prepare_prefill/prepare_decode 组装 input_ids 和 position；TP 张量并行下，仅 rank0 收集采样参数。所有 rank 共同执行 run_model 完成模型前向计算得到 logits；rank0 执行 Gumbel 采样得到新 token，其余 rank 跳过采样。最后 reset_context 清理临时上下文，rank0 返回生成 token 列表。

为什么采样只放在 rank0？

答：采样计算量很小，不需要张量并行；模型 forward 是重计算，需要多卡 TP 分担。只在 rank0 做采样，可以减少多 rank 之间大量 logits 广播通信开销，降低通信延迟。

  1. Prefill（is_prefill=True）
  • 输入：整条 prompt 所有 token
  • 计算：一次性算出 prompt 所有位置的 KV 并存入 PagedAttention 的 KV block
  • logits 只取最后一个 token的 logit，用来生成第一个输出 token
  1. Decode（is_prefill=False）
  • 输入：每条序列仅 1 个新 token
  • 计算：读取已有 KV cache，新增 1 步 KV，单步推理
  • logits 直接用于采样，得到下一个 token

run_model

Prefill、强制 eager、batch 太大 (>512) 走原生 eager；小 batch decode 路径使用 CUDA Graph 加速。

@torch.inference_mode()

@torch.inference_mode() 是 PyTorch 的装饰器，用来包裹推理代码块，禁用 autograd 自动求导引擎。

大模型推理不需要反向传播、不需要计算梯度，开启这个可以省显存 + 提速。

@torch.no_grad()

只是不记录梯度，计算图相关基础设施还保留；张量依旧会追踪历史。

上下文管理器 (with)和函数装饰器(@)

torch.no_grad() 和torch.inference_mode()：PyTorch 里这类对象同时支持两种用法：

  1. with xxx: 包裹代码块
  2. @xxx 装饰函数，函数整体都在这个上下文内执行

example:

  • 装饰器（@xxx）：本质是可调用对象（函数 / 类实例）。@decorator等价于func = decorator(func)。要求对象实现__call__方法。
  • 上下文管理器（with xxx:）：要求对象实现 __enter__ 和 __exit__ 方法。

capture_cudagraph

  • capture_cudagraph 用于预录制 decode 阶段多 batch 档位的 CUDA Graph。
  • 先分配最大 batch 尺寸的固定 buffer；逆序遍历 batch 档位，由大到小录制，共用同一个显存池。每个 bs 录制前执行 warmup，再进入 cuda.graph 上下文捕获模型前向的全部 CUDA 算子；录制完成保存 graph 和 buffer。推理时复用固定 buffer，调用 replay 重放，消除 Python 层 CUDA kernel 调度开销，降低 decode 延迟。

getattr(obj, 属性名, 默认值)

  1. 尝试读取 hf_config.head_dim
  2. 如果 hf_config 有 head_dim 字段 → 直接取这个值
  3. 如果没有这个字段（老版本模型 HF 配置没有单独存 head_dim）→ 使用后面的默认表达式值

MHA（多头注意力）

num_attention_heads = num_key_value_heads
32 个 Q 头，32 个 KV 头：
1 个 Q 头 对应 1 个 KV 头，此时可以粗略理解：一个 KV 头就是一个注意力头。

GQA（分组查询注意力，Qwen/Llama3）

例：32 Q 头，4 KV 头

  • 总共有 32 个注意力头（Q 头）
  • 只有 4 组 KV 头
    每 8 个 Q 头共享同一个 KV 头
    此时：KV 头 ≠ 注意力头。
    8 个独立的注意力头，共用同一套 K/V 缓存。

pin_memory=True

pin_memory=True：把 CPU 这块内存标记为「不可被操作系统 swap 换出到磁盘」的锁页内存，提升 CPU→GPU 之间内存拷贝速度。

普通 CPU 内存（pageable 可分页内存）：
操作系统可以把内存页面换出到 swap 磁盘分区。
当执行 tensor.cuda() 拷贝数据到 GPU 时，CUDA 驱动要先临时复制一份到内部锁页缓冲区，再传给 GPU，多一次拷贝，速度慢。

pin_memory=True 分配的内存（pinned memory）：
这块内存不会被 OS 交换到磁盘，CUDA 可以直接访问这块内存，省去中间临时拷贝，Host（CPU）→Device（GPU）传输更快。

nanovllm/utils/context.py

Context 是单轮推理的上下文容器，专门存放 PagedAttention 分页注意力算子运行所需要的全部参数。每个 ModelRunner 子进程维护一份全局单例 _CONTEXT，在每一次模型推理前填充、推理结束后清空。

  • 这段代码定义了存储 PagedAttention 推理信息的全局单例 Context。使用带 slots 的 dataclass 节省内存；
  • Context 存放 prefill 标记、cu_seqlens、slot_mapping、context_lens、block_tables 等分页 Attention 所需参数。
  • set_context设置本轮 batch 的上下文，get_context读取，推理结束reset_context清空全局上下文，防止上一轮数据残留干扰下一轮推理。

_CONTEXT = Context()

  • 全局单例对象：整个 ModelRunner 进程只有一份全局上下文_CONTEXT，保存当前这一轮推理的所有 PagedAttention 参数。

整体工作时序（非常重要）

  1. 准备 batch，调用set_context()，填充本轮推理的 PagedAttention 信息；
  2. 在run_model内部context = get_context()拿到全局上下文，供模型、CUDA Graph 读取 block_tables/slot_mapping；
  3. 推理完成，调用reset_context()，把全局上下文重置为空 Context，避免脏数据。

global关键字

Python 函数内部：

  1. 如果给变量赋值，Python 默认认为这是函数内局部变量，不会去外面找同名全局变量；
  2. 加上 global _CONTEXT，就是显式告诉解释器：

_CONTEXT 不是本函数的局部变量，使用模块顶层定义的全局变量，赋值操作修改的是全局那个对象。

nanovllm/layers/sampler.py

这个 Sampler 采用 Gumbel-max 采样。forward 先将 logits 转 float，除以 temperature 做分布缩放，softmax 得到概率；然后生成指数分布噪声，用 probs 除以噪声，取最大值索引，完成按概率采样。该实现只支持 temperature，没有 top_k、top_p 截断。使用 torch.compile 做编译加速。

@torch.compile

即时编译器（JIT Compiler）装饰器。

原生 PyTorch 默认是Eager Mode（动态执行）：Python 逐行执行，每调用一个算子就要和 GPU 通信，存在 Python 开销、多次 Kernel 启动开销、重复读写显存。

torch.compile 的工作流程：

  1. 追踪 (trace)：第一次执行被装饰函数，捕获里面所有 Tensor 运算，生成一张计算图，忽略无关 Python 逻辑；
  2. 图优化：做算子融合、删除冗余计算、优化内存读写；
  3. 生成 CUDA Kernel：编译优化后的代码；
  4. 后续调用：直接跑编译好的底层 kernel，跳过 Python 解释器，速度提升。

算子融合

算子融合是 GPU 优化里非常核心的手段，也是torch.compile提速最重要的手段

把多个连续的算子合并成单个 CUDA kernel。
中间的临时结果，保存在 GPU 片上寄存器 / Shared Memory，不写回全局显存。

例如，torch.compile可以把Sampler中这一串连续的张量运算融合成单个kernel，如果不融合，每一步都单独启动一个 CUDA kernel，中间张量反复读写显存；融合之后，中间变量不落地显存，直接在寄存器里链式计算。

不是所有算子都能融合，如果算子之间存在跨元素依赖等复杂依赖，就无法融合

div_

原地除法

  • 下划线 _ 是 PyTorch 约定：方法名以_结尾 = 原地操作。

  • a.div_(b)：等价于 a = a / b，直接修改 a 本身，不新建张量

  • 不带下划线版本 div()：a.div(b)，返回新张量，不会修改原张量

exponential_()

原地生成指数分布随机数

Gumbel 分布

冈贝尔分布，，是一类连续概率分布，常用于从离散类别分布做采样。

Gumbel 是一种概率分布。Gumbel-Max trick 是采样技巧：对每个类别概率加上独立 Gumbel 噪声，取最大值对应的类别，等价于按原始概率分布采样。利用数学变换，Gumbel 噪声可以由指数分布生成。nano-vLLM 的 Sampler 使用 Gumbel-max 替代 multinomial，整套算子容易被 torch.compile 融合加速。

@dataclass装饰器

自动帮你生成样板代码：

  • __init__ 构造函数
  • __repr__ 打印对象（方便 debug）
  • __eq__ 对象相等比较
  • 还有__hash__等

默认 Python 对象底层用__dict__字典存储实例属性。字典是哈希表，会有额外内存开销，还允许动态新增属性(Python普通实例自带__dict__，它是一个哈希字典，你可以随时给对象挂载新属性);

一旦开启 @dataclass(slots=True),等价自动生成 __slots__，会移除实例的__dict__,因为没有__dict__字典来存放新的属性键值对，对象能拥有的属性被__slots__固定死，只能使用类声明里写好的字段,不允许动态新增属性

post_init(dataclass 的后初始化钩子函数)

@dataclass 自动生成 __init__，执行流程：

  1. 自动 __init__：接收参数，给 self.temperature / max_tokens / ignore_eos 赋值
  2. 赋值全部完成后，自动调用 __post_init__(self)

专门用来做：参数校验、类型转换、初始化附属变量。

dataclasses.fields()

dataclasses.fields() 专门用来获取dataclass 类所有字段的元信息

  • 参数：必须是一个用@dataclass装饰的类（这里就是Config）
  • 返回：Field 对象列表，每个field对象描述一个类成员：名字、类型、默认值等
  • field.name,每个 Field 对象的.name属性，就是字段的字符串名字

nanovllm/config.py

说明：

  • max_num_batched_tokens: int = 16384,调度器单次step，batch 里允许的token 总数上限。Prefill 阶段很关键，用来防止单次 batch token 太多打爆显存;

  • max_num_seqs: int = 512,同一时间，调度器最多能同时容纳多少条并发序列（请求），最大并发数;

  • max_model_len: int = 4096,单条请求最大上下文长度（prompt + 生成 token 总和上限）;

  • gpu_memory_utilization: float = 0.9,GPU 显存利用率目标，0~1。用来预留一部分显存，剩下分配给 KV Cache（nano-vllm 简化实现，vLLM 里用来自动计算 KV cache 可占用空间）;

  • tensor_parallel_size: int = 1,张量并行 TP 的 world_size，也就是rank 进程总数。默认 1 = 单卡单进程；TP=2 就是 2 个 rank，2 张 GPU;

  • enforce_eager: bool = False,开启 CUDA Graph（图捕获），提前捕获 decode 阶段完整 GPU 计算流程，后续直接回放整张图，省去 Python 到 GPU 的多次 kernel 调度开销，token 生成速度更高、吞吐更好（消除多次 kernel launch 带来的 CPU-GPU 调度开销）

  • enforce_eager = True 强制 Eager 模式

关闭 CUDA Graph，每一行 PyTorch 算子遇到就立刻下发 GPU 执行，便于调试，推理性能下降。

  • hf_config: AutoConfig | None = None,HuggingFace 模型的 config 对象，保存模型原生参数：hiddensize、numattention_heads、max_position_embeddings 等，`__post_init`自动加载;

  • eos: int = -1,EOS 结束符 token id，LLMEngine 里加载 tokenizer 之后会覆盖这个值，用来判断序列生成结束;

  • kvcache_block_size: int = 256,PagedAttention 页大小！ KV Cache 每个 page (block) 能存放多少个 token。这里默认 256;

  • num_kvcache_blocks: int = -1,KV Cache 总 page 数量。-1代表自动根据显存利用率计算，也可以手动固定页数

面试高频问题

Q：max_num_batched_tokens 和 max_num_seqs 区别？

  • max_num_seqs：并发请求条数上限，限制多少条请求同时跑；
  • max_num_batched_tokens：batch 总 token 上限，Prefill 长 prompt 的时候，哪怕 seq 数量很少，token 总和也很容易打满这个上限，Scheduler 会截断 batch。

Scheduler 调度选 batch 的时候，两个条件同时判断，任意一个触发就不再加入新序列。

Q：kvcache_block_size 是什么？

PagedAttention，KV Cache 不再是连续大数组，切成很多固定大小 page（block）。block_size 就是一页能存多少 token。

256 代表：每个 page 存 256 个 token 的 K、V 向量。序列的 KV cache 由若干离散 page 链表组成，可以动态分配、复用页面。

Q：max_model_len 为什么取 min？

模型位置编码有上限，比如 Llama2 4096，你不能让输入超过模型原生支持的上下文窗口，否则位置编码越界，输出完全错乱。

Q：tensor_parallel_size 在这里限制 1~8 的原因？

这是 nano-vllm 简化设定，单机 GPU 数量一般最多 8 卡。多机场景这个限制会去掉

nanovllm/engine/sequence.py

  • 这是nano-vLLM 极简版推理引擎里的 Sequence（序列）类，对应大模型推理里的一个请求会话。
  • vLLM 核心就是 Sequence + KV Cache PagedAttention（分页 KV 缓存，block 块管理）。
  • 这个类用来保存单条推理请求的全部状态：prompt token、生成的新 token、缓存块表、调度状态、采样参数，并且实现了轻量化序列化（getstate / setstate），用于状态保存 / 迁移。

self.last_token = token_ids[-1]

  • 保存当前序列最后一个 token id;
  • 大模型自回归生成，下一个 token 只依赖序列末尾，缓存这个值避免每次取token_ids[-1]，方便 decode 阶段快速访问。

self.num_tokens = len(self.token_ids)

当前序列总 token 数量，初始就是 prompt 长度；后续每生成一个 token，append_token会把这个值 + 1。

self.num_prompt_tokens = len(token_ids)

  • prompt 的 token 总数，一旦初始化，全程固定不变！
  • 用来区分哪部分是输入提示词，哪部分是模型输出。
  • 后续计算生成 token 数量：总token - num_prompt_tokens。

getstate 和 setstate

这两个是 Python pickle 的自定义序列化 / 反序列化钩子，成对工作，nano-vLLM 做了空间优化。

__getstate__：序列化（保存对象），决定要存哪些数据
__setstate__：反序列化（恢复对象），用保存的数据重建对象

__getstate__：pickle 准备保存对象时自动调用，拿你自定义的状态元组
__setstate__：pickle 恢复对象时自动调用，把刚才存的元组还给你

__getstate__ 是 Python pickle 序列化的自定义钩子函数。
当对 Sequence 对象执行 pickle.dump() / pickle.dumps() 序列化时，Python 不会直接把对象全部成员打包，而是调用 __getstate__，把它返回的元组作为对象状态保存。

nano-vLLm 这里的目的：精简序列化数据，减少存储 / 传输开销。

设计目的：

  • decode 长文本生成时，token_ids列表会越来越长。
  • 如果每次做状态迁移 / 快照都序列化几万条 token，序列化耗时、内存占用巨大。
  • 引擎在 decode 阶段做自回归，只依赖最后一个 token，所以牺牲历史 token 存储，换取序列化性能。
