异构计算

异构计算：使用多种不同架构的计算芯片协同完成计算任务。

  • 同构：全部只用 CPU 计算（多个 CPU 核心，架构完全一样）。
  • 异构：CPU + GPU / NPU / FPGA / 专用 AI 加速芯片一起干活，不同芯片擅长做的事情不一样，分工合作。

常见异构硬件

  1. CPU：通用处理器，擅长复杂逻辑、分支判断、串行流程；并行能力弱。
  2. GPU（图形处理器）：大量小计算核心，擅长大规模浮点并行计算；AI 训练推理、矩阵运算、图像视频处理。
  3. NPU/TPU（AI 芯片）：神经网络专用硬件，专门加速矩阵、卷积，大模型推理。
  4. FPGA：可编程逻辑芯片，可以硬件电路重构，低延迟高性能。
  5. ASIC：定制专用芯片，硬件固化算法，功耗极低。

CPU 适合 “复杂、分支多、串行”；GPU/NPU 适合 “海量简单、高度并行”。

C++指针和引用的区别？

  1. 初始化：指针可以不初始化，也可以赋值为nullptr；引用定义时必须初始化，不能绑定空对象。
  2. 重绑定：指针可以随时修改，指向不同对象；引用一旦绑定某个变量，不能再绑定其他对象。
  3. 语法：指针用*解引用、->访问成员；引用是变量别名，直接用.访问成员。
  4. 内存：64 位下指针占 8 字节；引用逻辑上没有独立内存，底层编译器一般用指针实现，但编译器强制保证引用有效。
  5. sizeof：sizeof(指针)得到指针本身大小；sizeof(引用)得到所指向对象的大小。
  6. 其他能力：指针支持指针运算、多级指针int**，可以遍历数组；引用不支持引用的引用，也没有指针运算，只能绑定单个对象。

底层上，引用汇编层面本质就是指针，区别在编译器增加检查：保证引用不为空、不可重绑定。

使用场景：普通传参优先const T&，安全无拷贝；对象可能不存在用指针或者std::optional；需要多态、随时切换目标对象，用指针 / 智能指针；注意不要返回局部变量的引用。

C++ 虚函数原理

C++ 虚函数依靠虚表 (vtable)、虚指针 (vptr)实现多态。
含有虚函数的类，对象头部会增加一个虚指针 vptr，指向该类对应的虚函数表 vtable。虚表是全局数组，存放虚函数的地址。
调用虚函数时，运行期通过对象的 vptr 找到虚表，查表拿到函数地址再调用，实现运行时绑定（动态绑定）；普通函数是编译期静态绑定。

Son* p = new Son()指针类型和对象真实类型一致，编译器清楚对象类型，虚函数调用可被去虚拟化优化，能直接访问子类全部成员。
Base* p = new Son()是多态用法，静态类型是父类，编译期无法确定运行时真实类型，虚函数调用必须走虚表动态绑定，只能访问父类定义的成员。若父类析构不是 virtual，用 Base 指针 delete 会只调用父类析构，造成资源泄漏。

C++调用函数整个压栈过程是怎样的？

调用函数时，参数从右往左压栈 → 压返回地址 → 进入被调函数，保存旧 ebp → 开辟局部变量栈空间；函数返回时清理栈，跳回调用处继续执行。

1. KV cache的作用是什么？

大模型生成是自回归，每次只输出 1 个新 token。每一步做 Attention 时，历史 token 的 K、V 向量不需要重复重新计算，直接复用上次保存的 K、V，只计算新 token 的 K、V，大幅减少计算量，提升推理速度、降低延迟。

  • 不使用 KV Cache：每 decode 一步，把全部历史 + 新 token全部输入模型，重新对所有 token 算 K/Q/V，序列越长，算力开销越大（(O(n^2))）。
  • 使用 KV Cache：只对新生成 token计算 Q；历史 token 的 K、V 直接从缓存读取，只追加新 token 的 K、V 进缓存。Decode 阶段复杂度由(O(n^2))变成(O(n))。

进阶扩展

  1. KV Cache 存储内容
    每一层 Attention，保存所有已计算 token 对应的 Key、Value 张量。

Q 永远实时计算；K、V 缓存复用。

  1. PagedAttention（你代码里的方案）
    传统 KV Cache 是连续显存数组；PagedAttention 把 KV 缓存拆成固定大小block（页），用block_table记录每条序列占用哪些 block，slot_mapping映射 token 到物理 slot。
  • 好处：显存分配按需、碎片化更低，支持多序列并发调度；
  • 代价：需要专门的显存管理器调度 block，也就是你代码allocate_kv_cache预分配一大片 KV 显存池。
  1. 代价
    KV Cache 需要占用额外 GPU 显存，序列越长、batch 越大，占用显存越高；这也是 vLLM/nano-vLLM 要做显存利用率估算、限制最大并发序列的原因。

2. PagedAttention 解决了什么问题？

一句话：PagedAttention 核心解决传统 KV Cache 带来的 GPU 显存碎片化问题，提升显存利用率，从而提升推理服务的并发吞吐。

. 传统连续 KV Cache 有什么痛点（先讲痛点，再讲它解决了啥）

传统实现：每个请求的 KV 存放在一块连续的 GPU 显存里。

  1. 显存碎片严重
    不同 prompt 长度、生成长度不一样。请求结束释放连续内存块，会留下大量大小不一的空洞；新请求如果找不到足够大的连续块，哪怕总显存够用，也无法分配，只能拒绝新请求。
  2. 内存分配 / 释放开销大
    每次新建请求都要cudaMalloc，结束cudaFree，频繁调用 CUDA 内存 API，开销高。
  3. 预分配策略保守
    为了保证最大序列，要一次性预分配最大长度的连续 KV 显存，很多 token 位置全程闲置，显存浪费巨大。

2. PagedAttention 怎么解决（核心思想：分页，类似 OS 虚拟内存）

把整块 KV 缓存拆成固定大小的页（block，你代码里 block_size）。

  • 一个 block 存 N 个 token 的 K/V（例如 block_size=16，一页存 16 个 token）
  • 每个序列的 KV不需要连续显存；由block_table记录这个序列用到哪些离散 block 编号
  • slot_mapping：逻辑 token 位置 → KV cache 张量中物理 slot 索引，让 attention 内核能访问分散在不同 block 上的 KV

类比操作系统：
序列看到的是一段连续的虚拟地址空间；物理上分散在 GPU 显存的各个页，页表（block_table）做映射。

3. 它解决的核心问题（面试分点背诵）

  1. ✅ 消除 KV Cache 的显存外部碎片
    页面大小固定。请求结束只需要释放一个个独立 block，可以被其他请求复用；不需要找大块连续显存。总显存只要有空闲 page 就能分配，不再受连续空洞限制。
  2. ✅ 支持按需分配 KV 页面，减少显存浪费
    不用提前一次性分配最大序列长度的 KV；生成多少 token，分配多少 block。短请求不会占用超长预留空间，显存利用率大幅提升。
  3. ✅ 减少频繁 cuda malloc/free，提升分配效率
    提前一次性预分配一大片 KV 显存池（就是你代码allocate_kv_cache），后续 block 只做池内管理，不再向 CUDA 申请释放显存。
  4. ✅ 支持高效的序列复用（prefix cache，前缀缓存）
    多个请求共享相同 prompt 前缀时，可以共享同一批 KV block，不需要重复保存相同前缀的 KV，进一步节省显存。

4. 额外代价（面试官喜欢追问，一定要带上）

不是无代价：

  • 需要维护block_table、slot_mapping；Attention kernel 要根据 slot 索引读取分散 KV，内核实现更复杂。
  • 会引入少量内部碎片：最后一个 block 大概率填不满，会浪费 block 内少量 token 位置。

5. 精简口述版（面试直接说，约 1 分钟）

PagedAttention 借鉴操作系统分页内存的思路，把 KV cache 切分为固定大小的 block。传统 KV Cache 需要为每个请求分配连续显存，很容易产生显存碎片，显存利用率低，限制并发。
PagedAttention 允许一条序列的 KV 存储在离散的显存 block 里，通过 block_table 页表管理，按需分配页面。解决了 KV Cache 的外部碎片问题，提高 GPU 显存利用率，让服务可以同时跑更多并发请求。代价是内核更复杂，会存在少量 block 内部碎片。

高频追问

Q：slot_mapping 作用？
A：PagedAttention CUDA kernel 无法直接用 block_table(block_table在cpu)，slot_mapping把序列逻辑 token 位置，转换成 KV cache 张量里物理 slot 下标，给 attention kernel 用来寻址分散在不同 block 的 K/V。(slot:block 里面存单个 tokenKV 的格子)

Q：和普通分页内存区别？
A：PagedAttention没有磁盘 swap，全部在 GPU 显存，不换出到内存；只是借用分页的地址映射思想。

第一优先级（必学，面试高频，你现在正在看的）

1. Sequence、Scheduler 调度器（你刚读的这一大段代码）

这是推理引擎的任务管理层

  • Sequence：一条请求的完整生命周期封装（prompt token、已生成 token、状态、block_table、采样参数）
  • Scheduler 两个队列：waiting（待 Prefill） / running（Decode 中）
  • 调度策略：Prefill 优先；Prefill 按总 token 数限制 batch、Decode 按序列数限制 batch
  • Chunked Prefill：长 Prompt 分片 prefill
  • 抢占 Preempt：显存不足时踢出 running 里的序列，释放 KV，后面重跑 prefill
  • postprocess：模型跑完之后更新 seq 状态、判断 EOS、回收 KV block

面试常问：连续批（Continuous Batching）原理；prefill/decode 为什么 batch 约束不一样；抢占机制；chunked prefill 解决什么问题。

2. BlockManager + PagedAttention（核心中的核心）

vLLM 最标志性技术，也是 AI Infra 必考

  • KV Cache 不再是连续大数组，拆成固定大小 Block（页）；block 里面存若干 token 的 K/V
  • block_table：每个 seq 维护一张页表，记录该序列用到哪些 block，对应你前面看到的 block_tensors
  • block 分配、释放、引用计数
  • Prefix Cache（hash_blocks）：KV block 哈希，相同前缀请求共享 KV，减少显存与 prefill 计算
  • 理解 slot_mapping：把逻辑 token 位置映射到 GPU 显存物理 block+slot，是 PagedAttention 算子寻址关键

3. Prefill 和 Decode 两套数据流（prepare_prefill /prepare_decode）

理解两个阶段的差异，这是 LLM 推理最基础的分水岭

  • Prefill：一次性处理 prompt 全部 token，并行计算 KV；输入二维
  • Decode：每次仅输入 1 个新 token，自回归生成；输入一维
  • prepare_prefill：构造 cu_seqlens /cu_seqlens_q/cu_seqlens_k，用cu_seqlens变长标识
  • prepare_decode：context_lens，block_tables，slot_mapping
  • set_context /get_context：给 CUDA Graph 准备全局上下文

4. CUDA Graph 捕获与重放（capture_cudagraph /graph.replay）

推理性能优化重点，你前面看的capture_cudagraph

  • 什么时候捕获 graph：初始化阶段，提前录制 decode 计算流
  • 约束：tensor 底层显存地址不能变，只能原地改写（切片赋值），不能新建 tensor
  • graph_vars：预分配好的显存缓冲区，每次 replay 前原地写入新数据
  • 适用场景：Decode 阶段（计算图固定）；Prefill 不适合 CUDA Graph（输入长度变化）

面试问：CUDA Graph 原理、优缺点；为什么 prefill 一般不用 cuda graph；原地赋值的必要性。

spawn 工作原理

  • fork：复制父进程的内存空间（拷贝内存页），子进程一创建就拥有父进程所有变量、打开的文件、CUDA 上下文。(cpu适用)
  • spawn：
    1. 新建一个全新 Python 解释器进程
    2. 重新import 所有模块，从头执行代码
    3. 只把你显式传给 Process(args=...) 的参数，序列化（pickle）传递给子进程
    4. 子进程执行 target 函数

重点：spawn 不会继承父进程内存、变量、CUDA 上下文！
父进程里定义的变量，子进程默认看不到；只有通过 args 传过去的数据才会存在
nano-vLLM 这里选 spawn，核心原因：CUDA + GPU 场景不能用 fork。

优点（GPU 场景最关键）

  1. 安全支持 CUDA
    fork 会直接复制父进程 CUDA 上下文，子进程使用 GPU 会直接崩溃、出现 CUDA 错误。
    spawn 新开解释器，每个进程独立 CUDA 上下文，多 GPU 张量并行 TP 必须用 spawn。
  2. 干净隔离，进程之间内存完全独立，不容易出现内存脏数据、锁冲突。

缺点

  1. 启动慢：子进程要重新 import 全部模块、重新加载模型。nano-vllm 中每个 TP 子进程都会单独加载模型分片。
  2. 传参限制：传给子进程的 args 里的对象必须支持 pickle 序列化。像 GPU 张量、打开的文件句柄不能直接传

NVIDIA 集合通信库，专门给多 GPU 之间高速集合通信设计，是大模型张量并行 / 流水线并行的底层通信库,专门实现 GPU 集合通信算子。

  • allreduce（张量并行最常用，TP 做 Attention、MLP 时，多张卡求和归并结果）
  • allgather
  • broadcast
  • reduce
  • reduce_scatter

张量并行 TP 原理：一层矩阵切分到多张 GPU 分别计算，计算完allreduce把所有卡的结果求和，同步到每一张卡。这个 GPU 之间的数据传输就是 NCCL 完成。

  1. 直接 GPU ↔ GPU 通信，不走 CPU 内存
    数据直接从一张 GPU 显存拷贝到另一张 GPU 显存，绕过主机内存，速度远高于 Gloo（走 CPU 内存的通信后端）。
  2. 自动感知硬件链路：PCIe / NVLink。
    如果 GPU 之间有 NVLink，NCCL 会自动优先走 NVLink，带宽更高、延迟更低。
  3. 多进程、多节点都支持：单机多卡，或者多机器分布式都能用。
  4. 和 PyTorch 深度集成，torch.distributed指定backend="nccl"就启用。

大模型推理里的采样（Sampling）

大模型推理时每一步输出词表上的概率分布，采样就是从该分布选择下一个 token 的过程。
如果只用贪心取最大概率，生成内容容易单调、重复。采样通过 temperature、top_p、top_k 等参数，控制随机性，在保证通顺的前提下调节生成多样性。采样仅用于自回归推理，训练不需要采样。

1. 采样是什么？

大模型每一步输出，不是直接输出一个 token，而是输出一个概率分布（logits）：也就是下一个位置所有词表 token 各自的概率。
采样，就是从这个概率分布里，选出下一个 token 的过程。

简单一句话：

模型给出一堆候选词 + 各自概率，采样就是按规则挑出下一个词。

2. 为什么必须采样？

如果不采样，最简单做法就是直接选概率最大的 token → 叫Greedy（贪心解码），贪心其实也算一种特殊采样。
但纯贪心有明显缺点：

  1. 容易重复、呆板、局部最优，句子容易卡住循环，生成多样性很差；
  2. 没有办法控制生成随机性，写文案、聊天、创作场景不适用。

采样提供一套可配置策略，目标：
✅ 在生成质量和多样性之间做权衡。
通过SamplingParams里这些参数控制采样行为：

  • temperature 温度：调节分布平滑度；越高越随机，越低越接近贪心
  • top_p（nucleus sampling）：只取概率累积到 p 的一小部分候选词
  • top_k：只保留概率最高的 k 个 token
  • ignore_eos：是否忽略结束符，强制继续生成，你代码里就有这个参数

3. 两种典型采样（面试常问）

  1. Greedy 贪心采样：永远取概率最大 token，确定性输出，适合代码 / 数学推理，几乎无随机。
  2. 随机采样（带 top-p/top-k/temp）：按概率随机抽取，高概率词更容易被选中，但有机会选次优 token，适合对话、写作。

注意：训练阶段用的是 teacher forcing，不需要采样；采样只发生在自回归推理 decode 阶段（prefill 之后逐 token 生成）。

top_k

只保留概率最高的 k 个 token，剩下所有 token 概率直接置 0，再重新归一化采样。

top_p（核采样，nucleus sampling）

保留最小的候选集合，使得这些 token 概率累加 ≥ p，其余全部丢弃，再归一化采样。
不是固定个数，是按概率总和动态筛选候选词。

三者执行顺序：

  1. logits 除以 temperature
  2. 做 top_k 截断（去掉 k 名以外 token）
  3. 做 top_p 核截断（去掉尾部低概率 token）
  4. softmax 归一化
  5. 随机采样选出下一个 token

temperature 温度

缩放概率分布，控制随机程度

run 是 ModelRunner 单步推理入口。根据 is_prefill 标记，分别调用 prepare_prefill/prepare_decode 组装 input_ids 和 position；TP 张量并行下，仅 rank0 收集采样参数。所有 rank 共同执行 run_model 完成模型前向计算得到 logits；rank0 执行 Gumbel 采样得到新 token，其余 rank 跳过采样。最后 reset_context 清理临时上下文，rank0 返回生成 token 列表。

为什么采样只放在 rank0？

答：采样计算量很小，不需要张量并行；模型 forward 是重计算，需要多卡 TP 分担。只在 rank0 做采样，可以减少多 rank 之间大量 logits 广播通信开销，降低通信延迟。

@torch.compile

**即时编译器（JIT Compiler）**装饰器。

原生 PyTorch 默认是Eager Mode（动态执行）：Python 逐行执行，每调用一个算子就要和 GPU 通信，存在 Python 开销、多次 Kernel 启动开销、重复读写显存。

torch.compile 的工作流程：

  1. 追踪 (trace)：第一次执行被装饰函数，捕获里面所有 Tensor 运算，生成一张计算图，忽略无关 Python 逻辑；
  2. 图优化：做算子融合、删除冗余计算、优化内存读写；
  3. 生成 CUDA Kernel：编译优化后的代码；
  4. 后续调用：直接跑编译好的底层 kernel，跳过 Python 解释器，速度提升。

算子融合

算子融合是 GPU 优化里非常核心的手段，也是torch.compile提速最重要的手段

把多个连续的算子合并成单个 CUDA kernel。
中间的临时结果，保存在 GPU 片上寄存器 / Shared Memory，不写回全局显存。

例如，torch.compile可以把Sampler中这一串连续的张量运算融合成单个kernel，如果不融合，每一步都单独启动一个 CUDA kernel，中间张量反复读写显存；融合之后，中间变量不落地显存，直接在寄存器里链式计算。

不是所有算子都能融合，如果算子之间存在跨元素依赖等复杂依赖，就无法融合

面试高频问题

Q：max_num_batched_tokens 和 max_num_seqs 区别？

  • max_num_seqs：并发请求条数上限，限制多少条请求同时跑；
  • max_num_batched_tokens：batch 总 token 上限，Prefill 长 prompt 的时候，哪怕 seq 数量很少，token 总和也很容易打满这个上限，Scheduler 会截断 batch。

Scheduler 调度选 batch 的时候，两个条件同时判断，任意一个触发就不再加入新序列。

Q：kvcache_block_size 是什么？

PagedAttention，KV Cache 不再是连续大数组，切成很多固定大小 page（block）。block_size 就是一页能存多少 token。

256 代表：每个 page 存 256 个 token 的 K、V 向量。序列的 KV cache 由若干离散 page 链表组成，可以动态分配、复用页面。

Q：max_model_len 为什么取 min？

模型位置编码有上限，比如 Llama2 4096，你不能让输入超过模型原生支持的上下文窗口，否则位置编码越界，输出完全错乱。

Q：tensor_parallel_size 在这里限制 1~8 的原因？

这是 nano-vllm 简化设定，单机 GPU 数量一般最多 8 卡。多机场景这个限制会去掉

3.2 接受连接：接到线程池

void CServer::Start()
{
    auto self = shared_from_this();
    auto& io_context = AsioIOServicePool::GetInstance()->GetIOService();
    auto new_con = std::make_shared<HttpConnection>(io_context);

    _acceptor.async_accept(new_con->GetSocket(), [self, new_con](beast::error_code ec) {
        if (ec) { self->Start(); return; }
        new_con->Start();
        self->Start();   // 继续等下一个连接
    });
}

说明：

  • 每个连接绑定到池里的某个 io_context，避免单线程瓶颈。
  • Start() 递归挂新的 async_accept，形成持续监听。

3.3 HTTP 读 → 分发 → 写

void HttpConnection::Start()
{
    auto self = shared_from_this();
    http::async_read(_socket, _buffer, _request,
        [self](beast::error_code ec, std::size_t) {
            if (ec) return;
            self->HandleReq();
            self->CheckDeadline();
        });
}

void HttpConnection::HandleReq() {
    _response.version(_request.version());
    _response.keep_alive(false);   // 短连接

    if (_request.method() == http::verb::post) {
        bool ok = LogicSystem::GetInstance()->HandlePost(
            _request.target(), shared_from_this());
        if (!ok) {
            _response.result(http::status::not_found);
            // ...
        } else {
            _response.result(http::status::ok);
        }
        WriteResponse();
    }
}

说明：

  • 业务不在这里写，只负责协议层；具体逻辑全在 LogicSystem。
  • keep_alive(false)：一请求一响应后关连接，实现简单。

    它不是强制创建 N 个线程，只是给 asio 的一个建议值：提示 asio，你打算用多少个线程来调用 ioc.run()。

创建一个信号集合，绑定到 io_context ioc，监听 SIGINT 和 SIGTERM 两个信号。

  1. SIGINT：SIGnal INTerrupt
    控制台按下 Ctrl + C，终端发给程序的中断信号。
  2. SIGTERM：SIGnal TERMinate
    执行 kill 进程pid（不带 - 9），操作系统优雅终止信号。kill -9 是SIGKILL，无法被捕获，程序直接被内核干掉，没有机会执行收尾代码。

signal_set::async_wait()：异步等待信号事件

  • 调用之后不会阻塞当前线程，函数立刻返回；
  • 只是向 asio 事件循环注册一个回调函数；
  • 当操作系统发来我们监听的信号（SIGINT/SIGTERM），Asio 内部捕获，填充参数,这个 lambda 回调会被投递到ioc的任务队列，在ioc.run()的线程里执行。
  • if(error) == true：异步任务异常，直接 return，不执行 ioc.stop ()
  • if(error) == false：正常捕获到系统信号，继续执行 ioc.stop() 来优雅退出
  • ioc.stop();,把 io_context 标记为停止状态
    1. 不会立刻终止正在执行的回调；

    3. 当前队列中已经就绪的回调全部执行完，ioc.run()就会返回，解除阻塞。

7. acceptor、io_context、socket 三者关系

io_context 是事件调度器；acceptor 是 TCP 监听器，socket 是 TCP 通信端点；acceptor 和 socket 各自绑定 io_context，acceptor 负责接收连接，把新连接填入 socket，socket 负责收发数据。acceptor 绑定的 io 和 socket 绑定的 io 可以不是同一个（你的项目就是这种）。

io_context（IO 上下文）

作用：事件队列 + 回调调度器

  • 里面存放异步任务；调用io_context.run()的线程会取出任务、执行回调。
  • 所有 asio 对象（acceptor、socket）创建时必须绑定一个 io_context，不能悬空。
  • 一个 io_context 可以被多个 acceptor/socket 共用。

acceptor（tcp::acceptor，监听器）

  • 本质是listen 监听 socket，只负责监听端口、接收 TCP 连接，不收发业务数据。
  • 创建时绑定一个 io_context（你代码中是主线程的 ioc）。
  • acceptor 的async_accept事件、accept 回调，由它自己绑定的 io_context 调度（主线程执行 accept 回调）。
  • acceptor 的职责：当客户端三次握手完成，把新连接填充进你预先传入的 socket 对象。

⚠️ acceptor不会修改 socket 原本绑定的 io_context。

socket（tcp::socket，数据套接字）

  • 用来和单个客户端做数据读写（http 的收发）。
  • 创建的时候就绑定好 io_context（你代码里是 IO 池取出的 io_context，对应子线程），绑定后不可更换。
  • socket 的async_read / async_write等读写回调，由 socket 自己绑定的 io_context 调度（IO 池子线程）。

AsioIOServicePool

AsioIOServicePool 是基于 boost asio 实现的 io_context 线程池（IO 池），单例模式。预先创建一批io_context+ 工作线程；对外通过轮询，分配 io_context 给新连接，让不同 TCP 连接的读写事件分散在多个线程执行，充分利用多核 CPU，解决单 io_context 单线程串行处理的性能瓶颈。

CServer的acceptor 跑主线程 io，每一条新连接拿到池子里的一个 io_context，socket 绑定这个 io，读写回调在池子子线程跑。

_ioServices[i].run();

_ioServices[i] 是一个 boost::asio::io_context 对象。run() 是 io_context 的事件循环入口函数。

  1. run() 会阻塞当前调用它的线程；
  2. 不断从这个 io_context 的任务队列取出异步回调任务，在当前线程执行；
  3. 当满足退出条件时，run() 解除阻塞，函数返回，线程继续往下执行。

io_context 会不会被 “占用完”？

  • io_context 本身不是一次性资源，不会被取走消耗掉。

  • 池子里的 io_context 是常驻对象，GetIOService 只是返回它的引用，不是转移所有权，不是拿走、不是消费掉。

  • 多个 HttpConnection、多个 socket可以同时拿到同一个 io_context 引用，共用同一个 io。

  • 代码里一个 io_context 绑定一个独立工作线程

  • 同一个 io 上的所有异步回调，在对应的工作线程串行执行；

  • 多个连接共用同一个 io 是正常现象，只是负载均衡分摊。

  • 池子的 io 数量固定，不会动态新增；新连接来了只是复用现有的 io，不存在资源耗尽。

executor_work_guard 保活守卫

_works 保存一批 executor_work_guard 保活守卫，用来阻止 io_context.run() 在任务队列为空时自动返回，让 IO 工作线程常驻，持续等待新的异步网络事件。

1.LoginDialog::slot_login_mod_finish(ReqId id, QString res, ErrorCodes err)槽函数

HttpMgr 负责发送 HTTP 网络请求；当 HTTP 请求完成（成功 / 失败），HttpMgr 会发射 sig_login_mod_finish 信号，把 3 个参数抛出来

  1. 判断网络层面是否出错【ErrorCodes err：网络层面错误码（成功 / 超时 / 网络错误）】
  2. 将返回字符串解析为 QJsonDocument【QString res：后端返回的 json 字符串】
  3. 根据 ReqId，去_handlersmap 查找注册好的 lambda 回调，执行业务逻辑（登录成功后的处理）【ReqId id：请求ID，用来区分是哪一次http请求（登录、注册、找回密码等）】
  • jsonDoc.isObject(),如果原始 json 是{ ... }这种JSON 对象，isObject() 返回 true;如果是[ ... ]数组，或者不是合法对象，返回false
  • jsonDoc是QJsonDocument，jsonDoc.object()就是从 QJsonDocument 中取出根节点的 QJsonObject（也就是{ ... }大括号包裹的键值对对象）。
  • QMap<ReqId, std::function<void(const QJsonObject&)>> _handlers;,_handlers 是一个map 容器，用来存放不同网络请求对应的业务回调函数。

httpmgr.cpp

HttpMgr 是全局单例 HTTP 网络管理类，封装 Qt 的QNetworkAccessManager，专门统一发送异步 POST Json 请求，用信号槽把 HTTP 返回结果分发到对应的业务对话框（登录、注册、重置密码）。

核心设计思想：网络层 和 UI 业务层解耦

  • HttpMgr 只管发 http、收网络响应，不写任何登录 / 注册业务逻辑
  • LoginDialog / RegisterDialog 只需要监听对应模块的信号，处理返回的 json 数据

POST JSON 请求：使用 HTTP 的 POST 请求方法，请求体 (body) 里面放 JSON 字符串，同时在请求头告诉服务器：Content-Type: application/json。

application/json 是写在 HTTP 请求头 Content-Type 的值，专门搭配 POST（绝大多数场景） + 请求 Body 里面存放 JSON 字符串一起使用。作用是告诉服务端：本次 HTTP 的消息体（body）的数据是 JSON 格式，请用 JSON 解析器来解析 body。

HTTP 常见方法：

  • GET：参数一般放在URL 地址栏，没有请求 body，适合获取数据
  • POST：数据放在请求体（body），适合提交数据（登录账号、注册信息）

完整流程示例：

  1. LoginDialog 构造 QJsonObject，填入 email、passwd
  2. 调用HttpMgr->PostHttpReq
  3. HttpMgr：QJsonObject → 转 JSON 字节，设置Content-Type:application/json
  4. QNetworkAccessManager 发起 POST，把 JSON 塞进请求体发给服务端
  5. 后端收到 JSON，解析里面的邮箱密码，校验，返回 json 响应
  6. HttpMgr 收到后端返回，通过信号槽把返回字符串抛给 Dialog 处理

  • HttpMgr::GetInstance()得到的是shared_ptr，.get()：取出 shared_ptr 内部保存的原始裸指针 HttpMgr*
  • shared_ptr 是一个包装类，里面保存裸指针；shared_ptr ≠ 对象地址，类型不匹配，直接编译报错。
  • .get() 只是拿地址，不改变 shared_ptr 的 ref 计数。

说明：

  • 不是立刻马上 delete，而是：把这个 QNetworkReply 对象标记为待删除，等到当前 Qt 事件循环跑完之后，再自动 delete。

  • reply->finished这个 lambda 回调，本身还在 reply 对象触发的信号的调用栈里面。如果在信号回调内部直接delete reply，等于信号还没处理完，就把发送信号的对象销毁了，会造成野指针、程序崩溃。

  • deleteLater() 是 QObject 的成员函数，所有继承 QObject 的类都能用，QNetworkReply 继承 QObject。

  • 在 Qt 代码里写的 connect()，本质就是 QObject::connect()，二者是同一个函数，只是写法简写。

  • QObject 是 Qt 框架最基础的根类，几乎所有 Qt 核心类都继承它。
